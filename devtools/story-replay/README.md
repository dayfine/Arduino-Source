# Native offline checkpoint replay

This is the Arduino counterpart of [PokemonSimulation #73](https://github.com/dayfine/PokemonSimulation/pull/73).
It loads the actual evaluated FRLG Parcel capture, runs shared scenarios through
`Pokemon::build_story_checkpoint()` / `run_checkpoint()`, and checks semantic
walks, facing changes, map transitions, scene requests and outcomes. No console,
profile, save or controller is opened by the standalone tool.

```sh
cmake -S SerialPrograms -B build -DPA_FRLG_STORY_REPLAY=ON
cmake --build build --target StoryCheckpointReplay -j4
build/StoryCheckpointReplay > /tmp/frlg-parcel.replay.json
```

Configure from a clean committed tree so the tool records the actual build
revision. The executable uses embedded preview fixtures and does not fetch data
or run the console program. Native unit tests are registered as
`PokemonFRLG::StoryReplay`; the standard command-line test suite runs them.
GitHub CI builds/tests on the fork; Ubuntu additionally uploads
`frlg-native-replay-<os>-<compiler>` and compares against the pinned Python runner.

## Inputs versus expectations

`Programs/AutoStory/ReplayData/` contains exact `binding.json` / `cases.json`
copies from the immutable PokemonSimulation revision in `pin.json`. The capture
is `capture.json` there, the bytes of the old table export of 02.01 that
`binding.json` pins; the replay reads its checkpoint in the #312 step format
(a route's target and a step's direction as args). These are **PR #73
preview test fixtures**, not an approved resource/production-plan adoption.
The 53-map production resource pin is unchanged. Every selected native embedded
map must match its Python fixture's exact raw-byte SHA-256 before execution.

`route-candidate.json` is a separate **input**: the Python planner's actual route
actions. It is generated by `checkpoint_replay.run(binding, scenario)` and never
from `expectation.actions`. CI independently regenerates it from the pinned
Python implementation and checks it against the copied candidate. An assertion
cannot make the native executor walk a desired answer.

The native adapter validates that candidate against its own production movement
rules, then passes the resulting route to the existing `run_route()` with
scripted IO. It records requests before execution. An interrupted seven-tile
walk remains a seven-tile request; only its two possible positions survive,
with facing unknown. Later actions and saving must remain absent.

When `input.check_actions` is true, native tests and Python's existing checker
compare the **entire ordered semantic action list**, including an empty list for
a failed entry. There are no button counts or durations in those expectations.
The seven shared cases cover success, failed entry, missing scene observation,
missing receipt, wrong arrival, unconfirmed Mart transition and a Route 1
encounter. Ten native negative controls reject bad pins/bindings/policies/routes
and detect omitted, extra, reordered or incorrect actions.

## What is independently exercised

- The existing native checkpoint engine, including its explicit `from_save`
  initialization event. Its raw logs/pose/failure remain in the artifact.
- The existing native collision/warp/edge implementation, exposed by the narrow
  prediction wrapper. No second native movement model is added.
- The existing route runner with scripted callbacks. Source connection steps
  are annotated on supplied transition legs for the native hold model.
- A separate `OverworldSimWalker` timing control for uninterrupted routes,
  including fades and connection stalls; its status, position and violations
  are reported and checked for the successful case.
- The native story-cost planner and `follow_overworld_route()` as a separate
  alternative. Its legs are exported; they do not drive the supplied-candidate
  replay and are not required to equal Python's different-cost plan.

This is **Python-candidate replay on native code**, not proof that the native
planner chose the Python route, nor full live-executor parity. Exact native
planner-leg parity needs a separate matching-policy contract.

## Policy and evidence limits

The diagnostic explicitly binds one attempt, stop on interruption/failure and
no saving, matching Python's profile. It does not change the production game
executor or silently resolve console runtime options. Hops in supplied candidates are explicitly unsupported by this native importer;
no parity with Python’s ledge handling is claimed. Scene observations and
item receipts are synthetic; dialogue/animation and actual inventory are not
simulated. Native checkpoint bookkeeping does not become entry evidence.

The live executor still uses a nominal same-map STEP pose, authored scene
fallback and end-save behavior. The diagnostic instead resolves the predicted
warp and requires scripted scene evidence. The existing native C++-table versus
loaded-row simulation test preserves the live-wrapper behavior, separately from
this stricter profile. Production save/retry configuration remains unbound.
No native behavior fix is being hidden inside JSON loading.

The timing control has no encounters. The shared uncertain-encounter case uses
a deliberately scripted IO stop, not measured battle/detector timing. Queued
input, video recognition, real stillness, automatic recovery/rejoin and physical
controller behavior remain outside this conformance slice. Existing game-specific
simulation tests continue to cover their own cases.
