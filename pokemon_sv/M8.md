# M8: verify egg inventory and preserve the party across hatch attempts

Requested follow-up milestone: before farming starts, inspect the boxes and
ensure the box used by hatch quests actually contains eggs. The user should not
have to remember to leave the game on the correct box.

Status: documented; implementation and live validation have not started.

## Current behavior and motivation

In the current farmer, NUM_EGGS is a manually supplied count for the current box.
quest_hatch_egg() navigates to its hatch location before opening boxes, then scans
only the selected box for an occupied slot identified as an egg. It does not
choose a different box if that box has no eggs. On that path it logs
"No egg found during egg hatching quest!" and returns without the successful
path's box-exit/plaza recovery.

Relevant existing code:

- Options/PokemonSV_BBQOption.cpp: NUM_EGGS and OUT_OF_EGGS.
- Programs/Farming/PokemonSV_BlueberryQuests.cpp: quest_hatch_egg().
- Inference/Boxes/PokemonSV_BoxEggDetector.h: BoxCurrentEggDetector,
  BoxEggDetector and existing native detector tests.
- Inference/Boxes/PokemonSV_BoxDetection.h: slot/cursor and box-view detection.

These paths are relative to SerialPrograms/Source/VideoGames/PokemonSV. Inspect
the latest integrated code before implementation; this note records the behavior
observed in the original M5-era farmer.

## Confirmed restoration gap after a hatch timeout

On 2026-10-21 (PDT), the user noticed a different Pokémon in party slot 1 during
poor Auto Battle performance. A screen captured after the user stopped the run
showed a Lv.66 lead at 82/163 HP. No identity snapshot of the original lead before
the failing hatch is available, so the logs cannot prove which individual moved.

The earlier run provides a concrete failure sequence:

| Time | Event |
| --- | --- |
| 12:15:01.257652 | Requested swap of box row 0/column 0 with party row 0 |
| 12:15:04.722811 | Helper logged `Swapped slots.` |
| 12:15:12.477364 | Began waiting for an egg to hatch |
| 12:25:13.215394 | Threw `No more egg hatch after 10 minutes.` |
| 12:25:13.388376 | Program stopped; no reverse swap was logged |
| 12:28:50.086416 | Next farming run started |
| 12:30:12.628368 | Next hatch performed another box/party swap |
| 12:31:38.309199 | That later hatch requested its reverse swap after hatching |

quest_hatch_egg() calls hatch_eggs_anywhere() between the outbound and reverse
swaps, with no exception recovery around that call. The timeout bypasses the
reverse swap and leaves the intended party restoration unperformed. This is a
confirmed control-flow defect, consistent with the user's wrong-lead observation.
A later successful hatch restores the party it inherited; it does not recover
the original pre-timeout identity automatically.

Also, swap_two_box_slots() checks the source is occupied and sends swap commands,
but its `Swapped slots.` message is not a verified identity comparison. The trace
does not establish whether the initial egg classification or movement was correct,
nor why the first hatch timed out. Those remain separate investigation questions.

The [filtered timeout/restart log](fixtures/m8-hatch-timeout-party-restoration-2026-10-21.txt)
preserves both hatch sequences. No live reproduction was attempted while the user
was manually restoring the party. The code defect is not fixed by these notes.

Party preservation should be addressed before treating Auto Battle's low yield
as a navigation/spawn problem. The healing cycle in M9 is unconditional even with
a correct lead; an unsuitable lead can independently worsen kill yield.

## Intended flow

1. When hatching is enabled, open boxes before starting quest routes. Establish
   the view mode required by the egg detectors and inspect the current box first.
2. If it contains verified eggs, keep it selected. Otherwise search a bounded
   range of boxes and select a box containing eggs. Stop the search once a usable
   box is confirmed; avoid cycling indefinitely or scanning every box needlessly.
3. Record the selected box and verified egg positions/count. Log the selection
   and available count. Keep the configured egg count as a requested limit; do
   not assume that many eggs exist. If fewer are available, report that clearly
   and cap the usable inventory to the verified count.
4. Leave boxes and return to the expected overworld state before starting farming.
   Do not withdraw an egg during preflight: the existing hatch route deliberately
   waits until after navigation to avoid hatching en route.
5. Before withdrawing an egg for a hatch quest, recheck the intended box and egg
   slot. Update inventory after successful use; recover from an unexpected box
   change or depleted box with a bounded recheck/search.
6. If no eggs are available, honor the existing OUT_OF_EGGS policy: Stop, Reroll
   the hatch quest when encountered, or KeepGoing without attempting it. Startup
   inspection itself must not spend BP. If hatching is disabled/zero eggs are
   requested, respect that configuration instead of searching unnecessarily.

An unreadable or unstable box is an uncertain observation, not proof of zero
eggs. Retry within a bounded limit, then report a clear failure. Preserve all
Pokémon and the party; startup inspection must not move, release, or hatch any.

## Hatch failure recovery requirements

- Before the first swap, record and verify the original lead, the source box/slot,
  and the expected egg. Verify the party and box contents after each swap.
- Restore and verify the original lead on normal completion and recoverable hatch
  failure. On a timeout, do not simply let the exception bypass restoration.
- Cancellation or a crash may leave a cancelled controller context or unknown UI
  state. Do not blindly issue a reverse swap from a destructor/catch-all. Preserve
  enough recovery information and require startup verification before farming
  resumes; if recovery cannot be verified, stop with specific manual instructions.
- Do not allow a successful quest-board completion check to stand in for party
  restoration. The two postconditions are independent.
- Native C++ tests must cover a hatch function that throws after the outbound
  swap, interruption during either swap, restoration failure, successful hatch,
  and restart with a pending/uncertain restoration. Exercise the production
  coordinator through injected box/hatch actions, rather than only a decision
  function that cannot reproduce the failure between swaps.

## Acceptance criteria

- A correct current egg box stays selected; an empty or non-egg current box is
  replaced by a verified egg box without manual setup.
- Mixed boxes are supported: use only verified egg slots and count only eggs.
- Too few eggs, no eggs anywhere in the allowed search range, unknown detector
  results, and box-navigation timeouts produce explicit, bounded outcomes.
- No normal Pokémon is withdrawn as an egg. No stale startup observation alone
  authorizes a later party swap.
- Missing eggs during a hatch quest leave boxes and recover to a defined state;
  they must not leave subsequent quest-menu reads running inside the box UI.
- Search limits and the selection rule are explicit and tested. If several
  boxes have eggs, prefer the current box, otherwise the first verified usable
  box in the search order. Automatic continuation across multiple egg boxes is
  a separate decision; it is not assumed by this milestone.
- Native C++ UnitTest/UnitTestDatabase cases cover selection, counts, mixed/empty
  boxes, uncertainty, bounded searching, depletion, and the no-egg policy. Use
  injectable game actions for control flow and existing/reference-frame detector
  tests for visual recognition. No Python/source-extraction test harnesses.
- A local build and real Switch run are required: verify box navigation, detector
  view-mode assumptions, retained box selection after closing/reopening boxes,
  correct egg withdrawal, party preservation, and no-egg recovery.

## Relationship to other milestones

M7 improves quest-board observation and reuse. M8 concerns box/egg observations;
reuse the same certainty/invalidation principles where useful, but do not expand
M7's quest-board optimization into egg handling implicitly. M5 supplies bounded
rerolls and M6 supplies failure actions; startup inventory should feed their
existing policies rather than invent a second spending/retry policy.
