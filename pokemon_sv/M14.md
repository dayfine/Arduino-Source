# M14: BP income and reroll expense in run statistics

Requested 2026-10-21 during the M7a/M7b trial. Status: DOCUMENTED; no code or
UI change implemented yet. Keep separate from the two M7 feature PRs.

Show BP earned, BP spent on rerolls, and net BP in the existing Current Run
statistics. Include a net BP/hour rate alongside elapsed time so a run with a
few high-value red quests can be compared with one completing many blue quests.
Use the existing stats lifetime/reset behavior for Current Run and any aggregate
view; keep counters consistent with the quest and save counters.

Record verified paid rerolls once, including planner policy rerolls and exhausted
quest rerolls. Do not count merely opening the confirmation, rejected payments,
uncertain outcomes or verification retries as another expense. Rewards must
include incidental completions, including Auto Battle 10 completed while doing
Auto Battle 30. Repeated reads must not credit the same quest twice; a later
new quest with the same enum must remain eligible. Distinguish observed BP
balance from inferred rewards/costs; do not display an uncertain estimate as an
exact reconciled balance. An occasional balance reconciliation should not add
an OCR read before every action.

Example motivating this request: the controlled M7 phase began at 14,100 BP,
then Auto Battle 30, Coastal Photo and incidental Auto Battle 10 produced only
three recorded completions despite substantially different rewards. Subsequent
failed Catch Any and Swimming Photo routes spent time and paid rerolls without
reward. The quest count alone concealed this cost. Final totals belong in the
linked run result, rather than assuming that every reroll log is a payment.

Validation: native C++ scenarios through the production accounting seam for
normal and incidental reward, multiple completions, same-enum new instance,
paid policy/failed-quest rerolls, unconfirmed payment, repeated verification,
and run reset/aggregate behavior. Full local build and live start/end balance
reconciliation required. Reuse recorded evidence to design cases; no Python
tests. Prioritize alongside M7 incidental accounting, with a small standalone
stats slice if accurate transaction events are already available.

Evidence: [M7 combined trial](lab/runs/2026-10-21-m7b-live/RESULT.md).
