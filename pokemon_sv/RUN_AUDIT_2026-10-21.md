# BBQ farmer audit: 2026-10-21

All times are America/Los_Angeles (PDT). Scope: all eleven BBQ Solo Farmer starts
found in today's primary application/profile logs, ending with the user's stop
at 15:30:53 and switch to Flying Trial at 15:30:59. Overnight Flying Trial,
previous-day M3 runs, build/test logs and duplicate error-report copies are
excluded. No controller commands, settings or application binaries were changed

## Main findings and priorities

1. **Persistent retry/fallback integration is the largest immediate safeguard.**
   The final M5 run repeatedly reset failed quest budgets between batches. Eight
   Sneak Up dispatches failed (16 attempts); six Savanna photo dispatches failed
   (12 attempts), then another photo dispatch was interrupted. Three Catch Any
   dispatches failed (six attempts). This is direct baseline evidence for M4/M6,
   not a claim that the newer PR implementations were running or failed.
2. **New [M12](M12.md): shared Pride Rock target acquisition.** Catch Any, Sneak
   Up and Savanna photo use the same timed approach. They consumed 66.00 minutes
   of final-run dispatch time, including 63.09 minutes ending in failure. Capture
   target availability/arrival/framing before changing timing or detection.
3. **New [M13](M13.md): nested map recovery.** A Catch Ground return to plaza
   consumed 8m49.89s and logged 35 navigation exceptions before recovering.
   Inner 17-probe limits sit inside an unbounded outer return loop. Also track
   the source-only unreachable wall-escape exhaustion branch.
4. **[M8](M8.md) is a correctness prerequisite.** Hatch timeout skipped party
   restoration. After the user repaired the lead, two Auto Battle completions
   took 3m47s/4m09s, versus 10–12 minutes in the known wrong-lead run. This is
   supporting evidence, not a controlled benchmark of lead identity alone.
5. **[M7](M7.md) needs whole-board accounting as well as fewer reads.** One Polar
   photo removed both Polar Photo and Swimming Photo from the observed board,
   but the completion counter initially rose by one. An old queued identity can
   later match a new quest of the same enum. Prompt logs also report `Photo not
   taken.` on routes subsequently confirmed successful.
6. **[M11](M11.md) is intermittent, not permanently broken.** Eight wash attempts
   across the day produced two confirmed successes and six failed attempts.
   Failure occurred with both obstructed and clear views; furniture alone is
   insufficient as the explanation.

Suggested order: integrate/validate M4/M6 to stop repeated wasted batches;
preserve party through M8; investigate M12 and bound M13; improve washing through
M11 and board certainty/accounting/reuse through M7. Keep route fixes in separate
reviewable changes. Inspect the latest integrated PR architecture before coding.

## Additional issues and milestone evidence

### M4/M6: retries and spending policy

R11 is a concrete failing baseline for persistent budgets: the same outstanding
Sneak Up quest was tried in eight batches without removal; washing was tried
five times across three dispatches before eventual success. The running M5
binary did not contain M4/M6's new behavior. Eight explicit policy rerolls still
occurred in that run, while supported but repeatedly failing routes were left
on Run. A reroll counter alone therefore does not prove failed-quest fallback
is active. Validate the integrated state across batch boundaries and uncertain
board reads, with the configured fallback and one verified payment maximum.

### M7: simultaneous completion and diagnostic contradictions

At 13:23:53–55 the observed board was Polar Photo / Auto-10 / Swimming Photo;
the fourth slot had no OCR match. After one Polar-route photograph, the
13:25:01–03 board was Catch Psychic / Auto-10 / Tera-self. Both photo identities
disappeared; the counter rose from zero to one at 13:25:04. After Auto-10, a new
Swimming Photo appeared and the queued enum matched it. This is consistent with
two quests completing incidentally while only the dispatched quest was credited;
the logs cannot assign BP or a unique instance identity to either photo quest.

Track whole-board changes, incidental completion, same-enum replacement and
unknown fourth-slot presence explicitly. Do not compute actual BP or exact
in-game completion totals from the counter alone. Also, `Photo not taken.` was
logged at 13:24:29 and 13:29:33 on routes subsequently confirmed complete. The
prompt timeout is not authoritative negative evidence about taking a photo.

### Quest cap is checked at batch boundaries

R02 reached its configured three-completion trial target at 10:26:00, then
started another photo at 10:26:10. The user stopped it. The observed farmer checks
NUM_QUESTS in the outer loop, not before each dispatch in the current batch.
This proves an extra route can start after reaching the cap; no extra completed
quest beyond the cap was observed in that trial. Add a native integrated-loop
case and check the latest scheduler PR before making a separate change. This is
an additional stop-policy requirement alongside M4/M6/M7 integration, not a
request to revive an older Python test harness.

## Measurement limits and reproducibility

Sources: primary SerialPrograms logs under Profiles/bbq-m4 and Profiles/bbq-m5.
Other primary/default/profile logs were scanned for today's BBQ banners; none
added another run. The M5 binary was the original production build (timestamp
2026-10-20 22:59:18, production commit 53bed4b57), not the later native-test
refactor. M4 trials also precede its later PR rewrite. The notes do not validate
the newer implementations by attributing old runs to them.

- Run boundary: the exact `Starting Program: PokemonSV:BBQSoloFarmer` banner to
  `Program State: STOPPED`. Start requests/preflight can precede that boundary.
- Completion: `[Program]: Quest completed successfully.` or the explicit
  incidental-completion message (none observed). Counts reconcile with each
  run's available Current Stats counters. They are logged classifications;
  uncertain OCR can still misclassify game outcomes.
- Dispatch: program-level Doing quest to success/failure or run stop. Route
  labels inside identify attempts. A timeout-terminated hatch is separate from
  a normal failed return; interrupted routes are not treated as successes or
  silently removed from elapsed time.
- Read interval: `Reading quests.` to the subsequent B-mash close command.
  Three matched labels can be a valid three-quest board or a missed fourth slot;
  do not infer the distinction from match counts alone.
- Processing used local log parsing, not a test of production code. No Python
  tests were added. Future regression tests must use native C++ production seams.
