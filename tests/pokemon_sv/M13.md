# M13: bound nested plaza and map recovery

Status: new finding from the 2026-10-21 daily audit; no implementation.

## Recorded example

During R09 (profile bbq-m5, original M5 production binary), the second Catch
Ground attempt tried to return to Central Plaza at **11:18:11.043625 PDT**.
The first successful fly afterward was **11:27:00.933984**: **8m 49.89s** later.
The quest was eventually confirmed complete at 11:27:48.694928.

Within that return interval the log contains:

- 33 exceptions reporting that no Pokecenter icon could be found at the maximum
  warpable zoom level;
- two exceptions reporting a detected Pokecenter without a Fly menu item;
- 33 internal restart messages (32 with `menuitem`, one with `menu item`);
- two outer `Failed to return to Pokecenter. Closing map and retrying.` messages.

This recovered eventually and did not crash. It nevertheless consumed most of a
14.02-minute catch dispatch. The exception count is not 35 farmer quest attempts:
these are nested navigation probes inside one route attempt.

## Established control flow

Programs/PokemonSV_WorldNavigation.cpp, fly_to_closest_pokecenter_on_map(), bounds
its adjustment-table probing to 17 tries in each relevant stage. However,
Programs/PokemonSV_Terarium.cpp, return_to_plaza(), wraps that helper in
`while (!returned_to_pokecenter)` and catches failures to retry without a total
return deadline. Its `laggy` fallback changes the initial cursor push but does
not bound further retries. M4/M6's outer quest attempt count cannot act while
navigation remains inside this loop.

The trace demonstrates prolonged recovery, not its visual cause. Icon overlap,
map position/zoom, cursor timing and an incorrect starting state must be
distinguished with captured frames before tuning navigation.

Adjacent source-inspection finding: jump_off_wall_until_map_open() loops with
`i < 3` but checks `i >= 3` inside the loop to throw its terminal failure. That
branch is unreachable, so exhausting all three tries can fall through normally.
No matching wall-escape failure was demonstrated today; track this as a source
defect to cover, not an explanation of the observed map loop.

## Proposed work and acceptance

1. Give the complete return/recovery operation an explicit elapsed-time and/or
   attempt budget spanning nested helpers. Log stage, number of probes, elapsed
   time and the reason for changing strategy. Inner retries must not reset the
   outer budget.
2. On exhaustion, expose a navigation failure to the farmer; do not continue as
   if arrival succeeded or silently reroll while location remains unknown.
   Preserve a verified safe exit when possible and clear manual recovery guidance
   otherwise. M6's failure action must run only with valid UI/location state.
3. Keep cancellation and shiny-stop signals propagating. Audit broad catches
   when introducing the boundary; do not convert cancellation into another retry.
4. Make wall-escape exhaustion observable and verify map-open success before the
   caller proceeds. Use native injected failures to exercise all three attempts.
5. Native C++ UnitTest/UnitTestDatabase tests must exercise production navigation
   orchestration through injected map/fly/time actions: repeated inner failure,
   success on a later probe, outer budget exhaustion, wall-escape exhaustion,
   cancellation and interrupted battle recovery. No Python/source-extraction tests.
6. Local build and a short bounded real-console failure trial are required for
   navigation changes. Capture map zoom, cursor/icon positions and selected menu;
   do not deliberately recreate nine minutes of blind retries.

The [daily audit](RUN_AUDIT_2026-10-21.md) and its filtered events preserve the
timestamps/messages. This is separate from M9's unconditional healing/travel
policy and M12's target acquisition, though both routes can enter this helper.
