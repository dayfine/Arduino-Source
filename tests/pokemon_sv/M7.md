# M7 investigation: repeated quest-board reads

Evidence captured during normal M5 farming on 2026-10-21, America/Los_Angeles
(PDT), profile `bbq-m5`. Observed app source: M5 production commit `53bed4b57`
(PR [#1644](https://github.com/PokemonAutomation/Arduino-Source/pull/1644)); the
branch was at documentation commit `6cc56b6ca` during the run. This note is an
investigation input, not an implemented optimization or a complete M7 design.

## Observed example

After a quest completion at 11:51:17 (six recorded completions), the board was:

1. Wash Pokémon
2. Photo in Savanna
3. Travel 500 metres
4. Tera-self defeat, configured Reroll

The fourth slot was replaced by Make TM. The farmer read the board five times
before starting Wash Pokémon:

| Read start (PDT) | Caller / purpose | Board | Read start to close command |
|---|---|---|---:|
| 11:51:29.191705 | Farmer: choose work for a batch | Wash / Savanna photo / Travel / Tera-self | 4.00 s |
| 11:51:35.277034 | Reroll helper: revalidate expected board before spending | Same | 4.02 s |
| 11:52:05.619783 | Reroll helper: verify target-only replacement | Wash / Savanna photo / Travel / Make TM | 5.30 s |
| 11:52:12.960154 | Farmer: select work after old batch was discarded | Same replacement board | 3.69 s |
| 11:52:18.689479 | Farmer: check selected quest is still present before dispatch | Same replacement board | 4.44 s |

At 11:52:11.750678 the log reported
`Reroll replacement verified. Discarding the old batch.` At 11:52:23.965418 it
started `Quest: Give your pokemon a bath!`.

These are separate control-flow calls, not repeated failed OCR reads. All four
slots matched on each read. The five measured read intervals total **21.44 s**,
from each `Reading quests.` line to its subsequent B-mash command. This excludes
opening the panel and executing the queued close command (800 ms per call).
The whole span from the first read to bath dispatch was **54.77 s**; it also
includes reroll navigation/payment, menu transitions, and other overhead. Do not
attribute that entire span to OCR or claim it is all removable.

The log does not contain before/after BP measurements for this example, so it
cannot establish the reroll cost or reward credit.

## Call sites in the observed M5 source

- `PokemonSV_BBQSoloFarmer.cpp`, `BBQSoloFarmer::program`: one `read_quests` in
  the batch-selection loop, another before each queued quest is dispatched.
- `PokemonSV_BlueberryQuests.cpp`, `reroll_bbq_quest`: reads before payment and
  after payment (up to three verification reads if feedback is unclear).
- `PokemonSV_BlueberryQuests.cpp`, `process_and_do_quest`: reads after each
  quest attempt to determine completion; this explains the preceding 11:51:10
  read, which is outside the five-read span above.
- `read_quests` opens the panel, takes a video snapshot, reads four slots, and
  closes the panel each time. Call-site line numbers above apply to the M5
  commit; this independent notes branch does not include M5 implementation.

## Candidate improvement to investigate

Return a verified board observation from the reroll transaction and pass it to
scheduling. A batch boundary should invalidate the old board/work list, while
allowing the new verified observation to become the next batch's input. Evaluate
whether immediate dispatch can use that same observation when no intervening
work can change it. Avoid a cache whose validity depends only on elapsed time.

Represent observation certainty and slot presence explicitly: the existing
reader can omit a fourth slot when OCR returns empty. An uncertain/missing slot
must not become proof of quest completion, replacement, or safe payment.

First target: remove the immediate scheduling reread after a verified reroll.
Potential second target: remove the immediate pre-dispatch reread when its
observation is still valid. In this trace those two measured intervals total
**8.13 s**, excluding panel transitions. That is an opportunity from one trace,
not a measured speedup or a throughput forecast.

## Acceptance criteria for M7 work

- Replay this sequence with purpose-tagged read events and count actual reads.
  Once a replacement is verified, scheduling must not immediately OCR the same
  unchanged board again without an explicit invalidation reason.
- Keep the fresh pre-payment check and target-only post-payment verification.
  Never reuse the old batch's slot positions after a board mutation.
- Invalidate observations after quest attempts, rerolls, travel/actions that can
  complete quests incidentally, or external/unobserved board changes. Define
  how manual control and observation age affect validity before enabling reuse.
- Unknown OCR results, ambiguous fourth-slot absence, reordered boards, and
  simultaneous changes must fail conservatively. No extra paid confirmations,
  false completion credit, or refresh of an exhausted retry budget.
- Test no-mutation reuse, intervening incidental completion, stale pre-payment
  board, delayed replacement, and partial/unknown four-slot reads against the
  production control flow. Include M4/M6 state integration when combined.
- Measure read count and end-to-end time before/after on a comparable live run.
  Report OCR, panel transitions, and navigation separately; capture visible BP
  before/after for any live paid operation.

## Additional scheduling example: a newly observed red quest waits for old work

Same running M5 app/profile, 2026-10-21 PDT, later run starting at 13:22:35.
Wash Pokémon was first recognized at **14:08:53.503342**, but its route did not
start until **14:17:37.201549**: **8m 43.70s after the first logged recognition**.
The quest could have appeared before that observation; this is not an exact
appearance-to-start measurement.

| Time | Event |
| --- | --- |
| 14:08:53 | Completion check recognizes Wash / Pickup / Sneak-up / Savanna Photo |
| 14:09:00 | Previous Catch Electric quest confirmed complete |
| 14:09:10, 14:11:00 | Two Sneak-up attempts from the existing batch |
| 14:12:49 | Sneak-up exhausted retries; no completion |
| 14:13:04 | Dispatch Savanna Photo from the existing batch |
| 14:16:16 | Savanna Photo exhausted retries; no completion |
| 14:17:17 | After batch end, Pickup reroll verified; discard that batch |
| 14:17:37 | Dispatch `Quest: Give your pokemon a bath!` |

Wash was recognized correctly, is supported, and had no saved Skip override.
BBQSoloFarmer iterates a fixed quests_to_do list for a whole batch. Its reads
before/after an attempt check the current quest, but do not replace that list
with new work. A newly observed red quest is therefore not scheduled until the
old list finishes. On the next selection, the explicit Pickup reroll then
invalidated the proposed list (including Wash) and caused another read/selection.

This is a scheduling issue despite fresh OCR observations, not an OCR failure or
proof that red quests are unsupported. The [filtered log](fixtures/m7-red-quest-scheduling-delay-2026-10-21.txt)
preserves the board recognition, failed attempts, reroll and bath dispatch.

Alongside board reuse, evaluate replanning at safe quest boundaries when the
observed board changes. Decide explicitly how runnable bonus quests should rank
against old queued work and configured rerolls, so a cheap bonus task is not
needlessly delayed by long failing routes. Respect explicit exclusions, M4/M6
failed-quest state and payment verification. Do not interrupt a hatch, battle,
swap or other non-interruptible operation merely because a red quest appeared.

Add a native simulated scenario with a red quest appearing after a blue
completion; assert the chosen dispatch order, bounded reroll behavior, and no
extra retry budget. This priority-policy decision is proposed work, not an
implemented change or an assumption that every red quest must always run first.

## Whole-day audit: observation cost and completion accounting

The [2026-10-21 audit](RUN_AUDIT_2026-10-21.md) adds 210 board reads across the
three longer farming runs, totaling 24.25 minutes measured from Reading quests
to the close command (panel opening/closing execution excluded). The final run
alone has 114 reads / 14.14 measured minutes. These intervals overlap route
dispatch time and must not be added to it as a separate cost.

At 13:23:53–55, the board contained Polar Photo / Auto-10 / Swimming Photo.
After a Polar-route photo, the 13:25:01–03 board contained Catch Psychic /
Auto-10 / Tera-self; both photo identities disappeared, but Current Stats first
increased by one. A later new Swimming Photo matched the old queued enum after
Auto-10. Investigate whole-board incidental completion and quest-instance
identity rather than equating dispatched successes with actual rewards.

`Photo not taken.` also appeared on both successful Polar-route dispatches at
13:24:29 and 13:29:33. Treat a missing prompt as uncertain route feedback, not
authoritative proof that no photo or completion occurred. The audit fixture
retains these observations and the later board checks.

Add native integrated scenarios for simultaneous completions, a same-enum new
quest appearing before an old queued item is checked, and reaching NUM_QUESTS
mid-batch. The M4 trial began a fourth route after its third completion; stopping
at the requested cap needs a dispatch-boundary check in the integrated scheduler.
Check current PR behavior before assigning a separate implementation task.
