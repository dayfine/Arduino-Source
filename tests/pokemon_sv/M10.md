# M10: enable currently unsupported solo quests

Status: requested; planning only. Add support for Pickup first, then investigate
and validate the two disabled Flying-type routes. Treat each route as a separate
reviewable slice; do not enable all three by removing the capability filter.

## Current capability gap

| Quest | Current state |
| --- | --- |
| Pick up 10 items (`pickup_10`) | Excluded by not_possible_quests; the dispatcher entry is commented out and no active pickup route is implemented. |
| Catch a Flying-type Pokémon (`catch_flying`) | Excluded by not_possible_quests, although quest_catch has route code targeting Vullaby/Mandibuzz. Why it was disabled has not been established. |
| Photograph a Flying-type Pokémon (`photo_flying`) | Excluded by not_possible_quests, although quest_photo has Vullaby/Mandibuzz route code. Why it was disabled has not been established. |

Photograph a Pokémon in flight (`photo_fly`) is a separate, supported quest.
`UnableToDetect` is unreadable input, not another quest to implement. Multiplayer
gold quests remain outside the solo farmer's scope.

M5 adds explicit Skip/Reroll handling for unsupported quests; it does not make a
Run override enable an unimplemented or disabled route. Preserve that distinction
until a route is implemented and validated.

## Proposed slices

1. Pickup: record a real quest, verify which ground-item interactions advance its
   counter, then implement a bounded route to enough reachable items. Do not assume
   defeat drops count as pickups. Check position, successful interaction and quest
   progress; handle already collected items and insufficient reachable spawns.
   Stop or return failure when progress stalls instead of looping indefinitely.
2. Flying-type capture: inspect the existing route and why it was disabled.
   Validate target availability for the supported game version/location, arrival,
   target acquisition, battle entry and capture. Guard battle commands on observed
   battle state, retain shiny handling, and return a bounded failure on no target.
3. Flying-type photo: inspect the existing route and validate the target's type,
   visibility/framing and quest completion. A shutter press alone is not success.
   Reuse navigation with capture where appropriate without coupling their outcomes.

Only remove a quest's unsupported restriction when its active dispatcher, route,
error handling and tests are ready. Explicit Skip/Reroll policies must continue
working after support is enabled.

## Acceptance criteria

- Native C++ UnitTest/UnitTestDatabase cases call the production planner/route
  policy through injectable game actions. No Python/source-extraction harnesses.
- Each enabled quest has a bounded success path and bounded no-progress/failure
  path, with observed completion rather than assumed success after button presses.
- Tests cover eligibility before/after support, explicit Run/Skip/Reroll, missing
  targets/items, uncertain observations, interrupted navigation and retry limits.
- Local builds and real Switch runs are required for every enabled route. Capture
  before/after quest progress and visible BP, plus target/item acquisition evidence.
- Existing unsupported cases remain excluded until their own validation is done;
  multiplayer support is not implicitly introduced.

## Integration

Use the latest integrated quest identity/planner modules from the earlier PRs;
not_possible_quests and identity may move as those refactors merge. Respect M7's
observation certainty, M4/M6's retry/fallback policy, M8's party preservation and
M9's bounded-progress principle. Normal Pokémon and party state must not be
silently changed as part of a new route.
